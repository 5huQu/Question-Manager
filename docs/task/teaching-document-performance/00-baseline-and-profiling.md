# T0：基线、埋点与性能预算

## 目标

建立可重复的性能基线，确定三类慢操作中每个阶段的实际耗时和长任务来源。T0 不改变产品行为。

## 测试文档

至少建立三档合成 fixture，禁止使用真实用户文件提交到仓库：

- S：30 个顶层块、10 道题、少量公式与图片。
- M：100 个顶层块、40 道题、包含答案、解析、选项和知识卡片。
- L：300 个顶层块、100 道题，包含长段落、跨页题、图片和手动分页符。

每档都要覆盖学生版与教师版，并保持资源 URL 可重复、无外部网络依赖。

## 分阶段埋点

使用 User Timing API 或等价的轻量开发埋点记录：

1. 用户操作到控件状态更新。
2. 派生文档/variant 生成。
3. 隐藏测量树 React commit。
4. 字体、图片、题目资源等待。
5. choice layout 探测。
6. 块与段落 DOM 测量。
7. 纯分页规划。
8. 可见页面 React commit。
9. 操作到最终 settled。

埋点默认不得污染生产日志；应通过开发开关或 Performance 面板读取。

## 初始性能预算

以下是待 T0 数据校准的初始目标：

- 操作到首帧反馈 p95 小于 100ms。
- 已有缓存的视图或学生/教师版切换 p95 小于 150ms。
- 插入分页符到画布出现标记 p95 小于 100ms。
- M fixture 的后台精确分页 p95 小于 500ms。
- 用户交互路径不出现超过 100ms 的单个主线程长任务；目标值为不超过 50ms。
- 快速连续切换十次后只允许最后一个 generation 发布 settled 结果。

若当前硬件无法满足绝对值，报告必须同时给出相对改善目标，首轮至少降低 M/L fixture 的 p95 50%。

## 输出

- 基线结果表和性能时间线截图。
- 每个操作的主导阶段与占比。
- 确认 T1～T7 的优先级是否需要调整。
- 可自动运行的性能 fixture 或基准脚本。

## 验收

- 连续三轮测量结果波动范围可解释。
- 开发模式与生产构建结果分开报告。
- 埋点自身开销经过验证，不改变分页结果。
